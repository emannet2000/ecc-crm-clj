# Provider integrations and activation

This release implements Zoom meeting creation/update/cancellation, Google Calendar synchronization for explicitly connected ECC meetings, Stripe Checkout payment collection, and DocuSign signatures with signed PDF/certificate retrieval. These integrations are implemented but **not activated or verified against live provider accounts in this workspace**. No credentials or production target were available during implementation.

## Configuration

Use `deploy/integrations.env.example` as a private worker environment file. Set `INTEGRATIONS_ENABLED=zoom,google,stripe,docusign` on the API to enable requests. API processes need only that flag; provider secrets belong to the worker. Keep `INTEGRATION_NAMESPACE` stable and unique to this deployment, including after restoration. Never reuse a production namespace in a development database connected to the same provider accounts.

Run exactly one integrations worker per deployment; its DocuSign refresh token file must be private, persistent and writable by the worker. The queue uses database leases and deduplicates operations, but one worker also avoids racing rotation of the same OAuth refresh token. Do not store tokens in CRM tables, frontend configuration, repository files or chat messages.

- **Zoom:** activate a Server-to-Server OAuth app in the ECC Zoom account; configure account ID, client ID/secret and the authorized host user. Grant the required meeting read/write permissions. The worker requests account-credentials tokens and stores only the join URL, meeting ID and passcode, never Zoom's host start URL. New links retain the appointment's Internal/Client visible setting.
- **Google Calendar:** enable Calendar API, obtain user consent for Calendar event read/write access and offline access, and configure client ID/secret, refresh token and the calendar ID. Use a dedicated private staff calendar. Only appointments explicitly connected in ECC are synchronized. There is no import of unrelated personal events. Local changes update provider events, including cancellations; polling imports remote title/time changes and cancellation. Local edits win concurrent conflicts, and conditional ETags protect remote updates. No client invitations are sent implicitly.
- **Stripe:** configure a secret key from an account permitted to operate in ECC's country and currency. Begin with test mode. The portal exposes a hosted Checkout URL for an issued invoice's current remaining balance. Amounts come from the server ledger in exact minor units. Sessions use stable idempotency keys. A return URL never records payment; the worker fetches the session using server credentials, verifies the deployment/invoice/job identity, amount, currency and paid state, then posts exactly one receipt in the same transaction as its integration event. Changed/archived invoices cause unpaid sessions to expire. A payment that conflicts with a concurrent manual receipt goes to Review instead of overpaying the invoice. Gateway refunds, disputes, settlement reconciliation and chargebacks require a separate reconciliation workflow and are not automatically posted by this adapter.
- **DocuSign:** use a developer account initially, configure integration key/client secret, account ID, OAuth authorization host, account-specific `/restapi` base URL and the private refresh-token file obtained through authorized OAuth consent. Production requires the account's production API access and consent. The worker sends the issued contract's escaped terms with a signature tab and stable transaction ID. Clients sign through DocuSign's email. Contract validity is checked before dispatch; the sender account's envelope expiration policy applies after sending, rather than an automatically synchronized CRM deadline. The worker verifies completion with the provider, records acceptance and retains the exact combined signed PDF and completion certificate. The existing scanner quarantines those bytes before portal download. Portal ownership checks are repeated on every download. Portal click-to-accept is blocked while that contract has a pending/sent/uncertain signature request.

The implementation follows the providers' [Zoom OAuth](https://developers.zoom.us/docs/integrations/oauth/), [Zoom meetings](https://developers.zoom.us/docs/api/meetings/), [Google Calendar events](https://developers.google.com/workspace/calendar/api/v3/reference/events), [Stripe Checkout Sessions](https://docs.stripe.com/api/checkout/sessions), and [DocuSign envelope](https://developers.docusign.com/docs/esign-rest-api/reference/envelopes/envelopes/create/) interfaces. Production account eligibility and application approval must be checked with each provider.

## Staff workflow and recovery

Save/select an appointment, then choose **Create Zoom meeting automatically** or **Connect Google Calendar**. Select an issued contract and choose **Send selected contract for electronic signature**. Select an issued invoice and choose **Create secure payment link**. Use **Integration status** within the current client/application to inspect jobs and their redacted error codes.

Requests are queued transactionally with the activity event. The worker performs bounded HTTPS requests outside database transactions, disables redirects, restricts provider hosts, refreshes OAuth tokens, and persists results before notifying the assigned consultant. It checks pending payment/calendar records every minute and signature status no more frequently than once every 16 minutes per envelope, with a bounded batch of 50 per cycle; larger queues can take longer. The signature interval follows [DocuSign polling limits](https://developers.docusign.com/platform/webhooks/connect/). There are no unauthenticated webhook endpoints and no dependency on browser redirects for reconciliation.

Unknown create outcomes go to Review. **Retry selected integration request** reuses the original operation identity. Stripe's idempotency window and DocuSign's transaction lookup window are bounded; old ambiguous operations require provider-side reconciliation. Zoom creation recovery searches for the original marker and refuses another create when its outcome cannot be established. No blind retry can mint a new Zoom meeting after an ambiguous creation. Provider API failures and permissions need operator attention; fixing credentials does not prove an earlier operation failed.

Client-visible link/receipt/signature data is projected separately from staff job errors, OAuth tokens, audit data and internal notes. Download authorization and malware scanning apply even when a client changes a URL or document ID.

## Hosting

For a systemd host, install `deploy/ecc-integrations.service`, configure its private environment files and token file, and use the same database/timezone as the API and existing workers. Include the scheduler and every other database writer in deployment stop/start commands. For Render, run `python3 scripts/integration_worker.py` as a background worker using `deploy/Dockerfile.workers`; PostgreSQL may be shared across services. A SQLite deployment must run workers on the same host with the same local persistent disk, not on an independent Render background service.

For the root Compose deployment, copy the private worker config to `integrations.env` and add `-f compose.integrations.yaml`. Build the integrations image, initialize the named token volume with owner UID 10001 and mode 0600 for the refresh token, then start the services. The API's `INTEGRATIONS_ENABLED` value must match the enabled providers. Do not bake credentials into an image.

Apply SQLite migration `0018_provider_integrations.sql` or PostgreSQL migration `0005_provider_integrations.sql` using the existing API migration command, after a verified backup and with incompatible old writers stopped. They add durable jobs, provider links, immutable provider events and a worker heartbeat. Existing cases remain applications.

## Production deployment

`python3 scripts/deploy_integrations.py --binary PATH --web PATH --backup-dir PATH --service-commands PATH` performs preflight and outputs a read-only plan. The service command file contains argument arrays (no shell expansion); `deploy/integration-service-commands.example.json` is an example and must be adapted to the actual service names and **all** writers, including the scheduler and any backup manager that modifies application state. Run the tool under the configured private production environment.

The exact binary, web assets and migrations must have passed `scripts/check.sh` and have a sealed release manifest. Run provider sandbox smoke tests before sealing the release for production. Add `--apply` only on the chosen production host to execute: verified offsite backup and restore drill → stop all writers → final verified backup and drill → migrations → start API/workers → API readiness and worker heartbeat checks. Failed migration/start/health leaves writers stopped and preserves recovery evidence; it does not claim success or guess that an older binary can use the upgraded schema. Review recovery state before restoring or restarting.

The tool does not provision hosting, accounts, OAuth consent, DNS/TLS, a backup repository or provider credentials. Live deployment and account smoke tests remain blocked until those are supplied through the deployment environment. The full review is in `docs/CLIENT_JOURNEY_ACCEPTANCE.md`; passing local adapter tests is not evidence that every original specification requirement is complete.
